_Split out of `CLAUDE.md` on 10 Sep 2026. A cross-reference to a section "below" or "above" that is not in this file means the sibling file under `docs/`._

## Tooling notes

- Playwright MCP is registered twice on purpose. `.mcp.json` is the portable copy that travels with the folder; it needs approval on first session start, and `.claude/settings.local.json` pre-approves it via `enabledMcpjsonServers`. A local-scope copy also lives in `~/.claude.json` under this project, which needs no approval and takes precedence. Both point at the same persistent profile, `~/.cache/pw-jobapps`, so ATS logins survive between sessions.
- `claude mcp get playwright` reports the resolved scope and health. A newly registered server does not appear in the running session's tool list, because that is built at startup. Restart before expecting `mcp__playwright__*` tools.
- If a browser call fails with a missing-browser error, add `"--browser", "chrome"` to the args in `.mcp.json` to use system Chrome rather than installing a bundled Chromium.
- `~/.cache/pw-jobapps` is shared with the Research project's Playwright server. Chromium locks a profile directory, so do not run both projects' browsers at the same time.
- The lock also survives a dead session. `Browser is already in use for <user-data-dir>, use --isolated` (the directory named in `<profile>/browser.txt`) means some earlier `@playwright/mcp` process still owns it, not that anything is wrong with the config. On 10 Sep 2026 five of them were alive, one holding a Chrome that had sat on `about:blank` since the previous afternoon. `pgrep -f "user-data-dir=<user-data-dir>"` finds it. Killing it releases the lock and the browser relaunches on the next call, but the sandbox classifier blocks `kill`, so the user has to run it.
- The Playwright profile is its own browser profile, not the user's everyday Chrome, so a site the user is already signed into in Chrome is not signed in here. The user approved a LinkedIn sign-in on 9 Sep 2026. Sign in once inside the Playwright browser and it persists in `~/.cache/pw-jobapps` for every later session. Ask the user to type the LinkedIn password in the browser window rather than passing it as a tool argument.
- A helper file is wrapped as `("+code+")` before it runs, so it must be a bare expression. A trailing semicolon after the closing brace makes it a syntax error. Check one without a browser: `node -e "new Function('return ('+require('fs').readFileSync('pw/next.js','utf8')+')')()"`.
- `browser_run_code_unsafe` takes a `filename` instead of `code`, and the file is one self-contained `async (page) => {...}`. It is not a Node script. Version 0.0.80 runs it with `vm.runInContext` in a context holding only `page`, so there is no `require`, no `process` and no working dynamic `import`. A helper cannot read a file, take arguments or reach the environment. It can only drive the page. Per-Workday-page helpers are still worth writing during a live run, where each one can be verified.
- Do not bother with `--snapshot-mode none`. Version 0.0.80 already keeps snapshots out of the response, so it saves nothing.
- Changing the server's arguments means changing the local-scope copy in `~/.claude.json`, because that one takes precedence. Editing `.mcp.json` alone has no effect. Mirror the change into `.mcp.json` anyway so the folder stays portable, and restart afterwards.
- `python3 ats.py <url>` names the ATS behind a URL and, for Workday, fetches the posting from `/wday/cxs/{tenant}/{site}/job/{rest}`, which is the page URL with `/wday/cxs/{tenant}` spliced in and any `en-US` segment dropped. Whole postings, no browser, no bot wall. `python3 ats.py selfcheck` runs offline.
- HigherEdJobs detail pages now sit behind Incapsula and return a 1KB bot page to `curl`, so the 9 Sep 2026 sweep method needs the browser for detail pages. The sweep's `Apply URL` column holds HigherEdJobs links rather than employer links, so the employer ATS still has to be resolved per role.
- ApplyPilot's `src/applypilot/config/employers.yaml` was checked on 10 Sep 2026 and is 48 Canadian banks and corporates, zero higher education, so there is nothing to import. Its `sites.yaml` is a Canadian job-board registry plus a thin blocked list. What is worth knowing from that project is only the shape: tenant plus site id is enough to reach a Workday tenant's API, which `ats.py` now does.
- `.claude/settings.local.json` pre-approves the Playwright MCP server, `jobs.py`, `ats.py`, `mkemail.py`, `pgrep` and the liveness `curl`. A prefix rule stops matching the moment anything is appended to the command, so `python3 outreach/mkemail.py ... ; echo $?` is blocked while the bare call goes through. Keep pre-approved calls plain. `cat .claude/settings.local.json` is blocked too; read it with the Read tool. Each classifier stop costs a round trip and can cost a Workday session, so add a rule rather than re-approving the same command. A session must restart to pick up new rules.
- Creating or running a hook script is blocked by the classifier from inside a session, deliberately, since a hook runs automatically afterwards. The user has to install one by hand. The Stop hook that keeps a bulk run going lives in the session scratchpad rather than in `.claude/hooks`, and it only acts when `.bulk-run` exists in this folder.
- A liveness check has to be a GET, and a 200 is not proof the req exists. SilkRoad answers HEAD with 404 for a posting it serves fine on GET, and answers 200 for a job id that was never real. The only difference on the fake one is a title with no job in it, `- - Boston University`, which is what `prep.py` now keys on. Expect other ATSs to have their own soft 404, so treat `check in browser` and `likely dead` as questions rather than answers.
- `python3 prep.py selfcheck` covers the parts that have gone wrong before: the annualiser across hourly, biweekly, semi-monthly, monthly and yearly, the two clearance false positives, and the credential matcher. That last one matched the ordinary word "do" on its first run and marked the WGU req a skip, so the acronyms are now case-sensitive and only count next to the word that makes them a requirement. Run it after touching either regex.
- `python3 jobs.py selfcheck` verifies the tracker upsert logic and that the base resume still compiles to one page. Run it after editing `jobs.py`.
- pdflatex is at `/Library/TeX/texbin/pdflatex`. There is no latexmk on this machine.
- The Claude desktop app carries its own browser, `mcp__Claude_Browser__*`, which is a second browser with no stake in the `~/.cache/pw-jobapps` lock. Verified 10 Sep 2026: a HigherEdJobs detail page behind Incapsula returned the real posting text through `navigate` plus `get_page_text` with `max_chars`, where `curl` gets the 1KB bot page. So read-only recon, meaning HigherEdJobs detail pages, non-Workday postings and contact research, can run at the same time as an `apply` agent drives Playwright. That is the only part of Workflow C's serial browser phase the app actually breaks.
- It does not replace Playwright on a form, for three reasons that all still hold. There is no `--secrets` substitution, so a password would be a literal string in the transcript. The persistent profile holding the ATS logins belongs to the Playwright server. And `browser_run_code_unsafe` takes a `filename`, so a `pw/*.js` helper costs nothing to re-run, while `javascript_tool` re-sends the whole snippet on every call.
- Two app browser habits worth keeping. `browser_batch` runs several actions in one round trip, so navigate plus read is one call. And use `find` with a query rather than `read_page`, because a full accessibility tree costs what `browser_snapshot` costs and the same landmine applies.
- Unverified as of 10 Sep 2026: whether a spawned agent sees `mcp__Claude_Browser__*` at all, and whether that browser keeps a login between sessions. Recon from the main thread with `max_chars` bounded is fine either way, since the one-browser-agent rule is about the Playwright profile lock and this browser does not touch it.
- A fenced bash block in the app gets a Run button, so a command the classifier blocks is one click for the user instead of something to type out. That covers `pkill -f "user-data-dir=<user-data-dir>"` for a stale lock and the bare `python3 prep.py <url>` call. `read_terminal` reads the result back out of the user's terminal panel.
- Keep the stale-lock check as `pgrep -f "user-data-dir=<user-data-dir>" | wc -l`. Adding `-l` printed 13 full Chrome command lines and cost about 8,000 tokens on 10 Sep 2026. A live Chrome sitting on `about:blank` with `--remote-debugging-pipe` is a running server's own browser rather than a stale lock, so read the count before killing anything.

## Rules

- Create ATS accounts under the address in the active `<profile>/profile.md`. Since 9 Sep 2026 the user reuses one password on every ATS, stored as `ALL_ATS_PASSWORD` in `<profile>/ATS-CREDENTIALS.txt`. Do not pass it as a tool argument, because every MCP argument is a literal string in the transcript. Since 10 Sep 2026 the server is started with `--secrets <profile>/ATS-CREDENTIALS.txt`, which is read as dotenv, so `browser_type` and `browser_fill_form` substitute a value whose text is exactly `ALL_ATS_PASSWORD`. Pass that name as the text and the real password is typed into the field, while the transcript and the generated code show `SECRET_ALL_ATS_PASSWORD`. The flag also redacts the value out of anything the tools return.

  Verify the substitution once per session before using it on a registration form, because a failed lookup types the literal string `ALL_ATS_PASSWORD` and a registration form would then set that as the account password. Navigate to `data:text/html,<input id=x>`, type the name into it, and check the length with `browser_evaluate`. 16 means the lookup failed. On a failure fall back to the older way: the browser runs headed, so drive the form to the password field and ask the user to type it in the window. Never print the value, and never copy it into another file.
- Do not `cat`, `head` or `grep` `<profile>/ATS-CREDENTIALS.txt` in a way that puts its contents in the transcript. The sandbox classifier blocks that, and that is the intended behaviour.
- Never invent an answer on a form. `<profile>/profile.md` has a stop-conditions section; honour it. Never answer out of the other profile's files either: check `python3 jobs.py profile` before you start.
- Submit applications without waiting for approval, per the user's decision of 9 Sep 2026, but only when every answer came from `<profile>/profile.md`. If you had to decide an answer, show it first.
- Emails to a published address go without approval. Hold a derived address for a quick yes, because a wrong recipient cannot be recalled.
- Write like a person. Never use an em dash, in a cover letter, an email, a form field or a file in this folder.
- Resolve who actually receives an application before submitting. A LinkedIn offsite apply can lead to a staffing vendor rather than the employer whose page it sits on. See the Bristol Myers Squibb entry in `<profile>/LOG.md`.
- One tracker row per company and role. `jobs.py` upserts on that pair, so re-running with new fields updates rather than duplicates.
- **An ATS that requires a candidate account before it will accept an application** (ADP Workforce Now, Paycom, Workday, and others) is not automatically a `blocked`/`skipped` stop. Standing approval given by the user 16 Sep 2026, extended same day to LinkedIn: use "Sign in with Google" (the address in `<profile>/profile.md`) or "Apply/Sign in with LinkedIn" (already logged in) whenever the ATS offers either as a sign-in option, without asking again each time, **but only when doing so does not require typing a new password anywhere**. If the ATS only offers a plain email+password registration, or an OAuth provider other than Google/LinkedIn (Facebook, etc.), stop and ask first, since that is outside this standing approval. Confirmed same day on Diageo's Workday tenant: completing "Apply With LinkedIn" OAuth (granting profile access) can still be followed by Workday's own "Create Account" step demanding a brand-new Workday-specific password. When that happens, stop before typing any password, even though the OAuth step itself was fine. The rule is on the password, not the OAuth grant: an OAuth step that fully replaces password login is covered by this approval; an OAuth step that only pre-fills a profile ahead of a still-mandatory new password is not, and creating any new password stays hard-prohibited regardless of standing approvals.
